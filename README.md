# Car Rental System

## Опис
Консольна система для оренди автомобілів з підтримкою повного життєвого циклу оренди, бізнес-правил, штрафів та аналітики.


## Основні можливості

- оренда автомобіля
- повернення автомобіля
- перегляд доступних авто
- розрахунок вартості оренди
- застосування знижок (economy / premium)
- штрафи за прострочення
- аналітика оренд (Facade)
- збереження стану в JSON


## Архітектура

- Domain (бізнес-сутності)
- Application (use cases + бізнес-логіка)
- Infrastructure (репозиторії + JSON storage)
- Console (UI без бізнес-логіки)
- Facade (спрощений доступ до системи)


## Використані патерни

- Strategy (розрахунок знижок)
- Factory (створення клієнтів)
- Repository (доступ до даних)
- Facade (об’єднання use cases)



## Бізнес-правила

- авто не може бути орендоване двічі
- ціна залежить від типу клієнта
- premium клієнт отримує більшу знижку
- повернення може включати штраф
- штраф = 1.5x тарифу за день прострочення
- кожна оренда зберігається в історії


## Use Cases

- Rent Car (оренда авто)
- Return Car (повернення авто)
- View Cars (перегляд списку авто)
- Analytics (дохід + популярність авто)


## Тестування

- unit тести домену
- інтеграційні тести сервісів
- перевірка бізнес-правил
- перевірка persistence шару


## Відповіді на контрольні питання lab 34

### 1. Чому діаграми і backlog є частиною кодувальної роботи, а не “додатком до неї”?
Тому що написання коду без розуміння цілі - це марна трата часу. 
* **Беклог** визначає пріоритети (що ми робимо зараз, а що можна відкласти), що дозволяє керувати часом і фокусом. 
* **Діаграми** (UML, Sequence) - це архітектурний контракт. Вони дозволяють продумати зв'язки між класами, знайти логічні помилки ще до написання першого рядка коду та узгодити бачення системи. Вони направляють розробку, виступаючи своєрідним кресленням, за яким будується код.

### 2. Що таке вертикальний зріз і чим він кращий за хаотичне створення всіх класів наперед?
**Вертикальний зріз** - це реалізація одного конкретного користувацького сценарію "від початку до кінця" через усі шари архітектури (UI - Application - Domain - Infrastructure).

**Чому це краще:** Замість того, щоб тиждень писати класи бази даних або домену, які ніяк не взаємодіють між собою ("горизонтальне" програмування), ви створюєте одну робочу фічу (наприклад, "Оренда авто"). Це одразу приносить бізнес-цінність, дозволяє протестувати інтеграцію всіх шарів, перевірити правильність архітектури та отримати швидкий зворотний зв'язок.

### 3. Які інваріанти краще перевіряти в сутностях, а які в сервісах?
Правило розподілу відповідальності (згідно з Domain-Driven Design):
* **В сутностях (Entities / Value Objects):** Перевіряються внутрішні інваріанти, які не потребують знань про зовнішній світ. Наприклад: ціна не може бути від'ємною, ім'я не може бути порожнім, дата повернення авто має бути більшою за дату видачі.
* **У сервісах (Application Services):** Перевіряються бізнес-правила, які потребують звернення до інших сутностей або бази даних.

### 4. Навіщо відокремлювати Domain, Application, Infrastructure, Console?
Це реалізація принципів **Clean Architecture**:
- Domain - бізнес-логіка
- Application - сценарії використання
- Infrastructure - зберігання даних
- Console - інтерфейс користувача

Це дозволяє легко змінювати частини системи без її поломки.

### 5. Чому Lab 35 повинна будуватися саме на артефактах Lab 34, а не з нуля?
Тому що це імітує реальний процес розробки ПЗ (ітеративний підхід/Agile). Lab 34 створює базу системи, а Lab 35–36 її розширюють, як у реальних проєктах.
## Відповіді на контрольні питання lab 35
### 1. Чому persistence-шар повинен залежати від контрактів, а не навпаки?

Тому що контракт (інтерфейс) описує що система повинна робити, а persistence — як це зберігається. Якщо зробити навпаки, ти жорстко прив’яжеш бізнес-логіку до конкретної бази/файлу і втратиш можливість її замінити.

Наприклад, `ICarRepository` дозволяє підмінити JSON, Memory або SQL без змін у `RentalService`. Це і є принцип **Dependency Inversion (DIP)** — високорівневі модулі не залежать від низькорівневих, а обидва залежать від абстракцій.


### 2. Які з ваших бізнес-правил належать сутностям, а які сервісам?

**У сутностях (Car, Customer, Rental):**
- авто не може бути здане двічі
- авто не може бути повернуте, якщо воно не орендоване
- ціна не може бути від’ємною
- ім’я клієнта не може бути пустим
- розрахунок базової вартості оренди

**У сервісах (RentalService):**
- перевірка доступності авто в системі
- створення оренди тільки якщо авто існує
- застосування знижки залежно від типу клієнта
- оформлення повернення і нарахування штрафу
- контроль бізнес-сценарію “оренда → повернення”

 Коротко:  
- сутність = правила “всередині об’єкта”  
- сервіс = правила “між об’єктами”

### 3. Чому LINQ-запити мають бути частиною бізнес-сценарію, а не окремою “лабораторною прикрасою”?

Тому що LINQ — це інструмент реалізації бізнес-логіки, а не окремий шар.

Якщо ти робиш, наприклад:
- пошук доступних авто
- підрахунок доходу
- топ найпопулярніших авто

це вже **бізнес-операції**, а не просто “демо LINQ”.

Якщо винести LINQ в окремі “приклади”, він втрачає сенс і:
- дублюється
- не пов’язаний зі сценаріями
- не тестується як бізнес-логіка

 У правильній архітектурі LINQ живе всередині сервісів або фасаду, як частина use case.


### 4. Як обраний патерн проєктування допоміг уникнути жорсткого кодування поведінки?

Використання **Facade + Strategy/Factory (у твоєму проєкті)** дозволило:

- винести складну логіку з Console (UI)
- уникнути `if/else` по всій програмі
- централізувати бізнес-операції в одному місці
- легко додавати нові сценарії без зміни існуючого коду

Наприклад:
- без Facade → Console знає все (оренда, повернення, аналітика)
- з Facade → Console тільки викликає `facade.Rent()` або `facade.Return()`

 Це прибирає жорстке зв’язування і робить систему розширюваною.


### 5. Що саме Lab 36 повинна довести про ваш код після цієї ітерації?

Lab 36 має довести, що система:
- працює як єдиний інтегрований сценарій, а не набір класів
- легко розширюється без зміни ядра (SOLID + DIP)
- має покриття тестами для бізнес-логіки, а не тільки класів
- підтримує реальні use cases end-to-end
- дозволяє змінювати persistence або логіку без переписування системи
