# Defense Checklist — Підготовка до захисту

> Car Rent System · v1.0.0+ · Самостійна робота №29

## Головний сценарій демонстрації (3–5 хвилин)

1. **Старт** — `dotnet run` → меню консолі.
2. **Перегляд автопарку** — показати список авто: статус, ціна, модель.
3. **Оренда** — ввести існуючий `CarId`, тип клієнта `premium`, кількість днів → отримати `DiscountedPrice`.
4. **Повернення з штрафом** — повернути з числом днів більше початкового → система нараховує штраф.
5. **Аналітика** — показати загальний дохід і топ-3 орендованих моделей.
6. **Пошук за фільтром** *(розширення СР29)* — ввести максимальну ціну → pipeline фільтрує доступні авто.
7. **Тести** — `dotnet test` → 220+ тестів пройшло, coverage >91%.

## Негативний сценарій

**Спроба орендувати недоступне авто:**
- Ввести `CarId` авто, що вже орендоване.
- Очікуваний результат: система кидає `CarNotAvailableException`, UI виводить читабельне повідомлення без stack trace, стан автопарку не змінюється.

Це демонструє: domain exception, защиту інваріанту `Car.Status`, обробку в facade без падіння програми.

## 5 питань про архітектуру

### 1. Де у проєкті видно SRP/OCP/DIP?

**SRP:** кожен шар має одну відповідальність. `RentalService` обчислює бізнес-правила, `JsonCarRepository` зберігає дані, `ConsoleUI` відображає. Вони не знають один про одного безпосередньо.

**OCP:** `RentalFacade.SearchCars` приймає `CarFilterPipeline` — нові умови додаються через `pipeline.Add(...)` без зміни facade. `CustomerFactory` — єдине місце, де треба додати новий тип, але решта коду не змінюється.

**DIP:** `RentalService` і `RentalFacade` залежать від `ICarRepository` / `IRentalRepository`, а не від конкретних `JsonCarRepository`. Конкретна реалізація ін'єктується ззовні.

### 2. Чому Factory для клієнтів, а не простий `if`?

Factory (`CustomerFactory`) централізує логіку створення: нормалізацію рядка типу (`" Premium "` → `premium`), перевірку невідомого типу, повернення відповідного підкласу. Якби це було в `RentalService`, логіка створення змішалась би з бізнес-правилами. Factory — єдина точка змін при додаванні нового типу.

### 3. Як Observer використовується в проєкті?

`ApplicationEventBus` — синхронний event bus. `RentalService` публікує `RentalStartedEvent` / `RentalReturnedEvent`. Підписники (наприклад, логер або майбутній модуль сповіщень) реєструються через `Subscribe<TEvent>`. Бізнес-логіка не знає, хто слухає події — дотримується OCP і SRP.

### 4. Чому JSON, а не SQLite або база даних?

Для навчального console-застосунку JSON достатній: немає конкурентних записів, обсяг малий, не потрібна ACID-транзакційність. Водночас persistence ізольований в `Infrastructure` за `ICarRepository` — перехід на SQLite вимагатиме тільки нову реалізацію інтерфейсу, не торкаючись domain або application.

### 5. Що б ви реалізували після курсу?

Перший крок — async I/O для JSON repository (`await File.ReadAllTextAsync`). Другий — SQL persistence через Entity Framework Core. Третій — Web API поверх того ж application layer: `RentalFacade` вже не залежить від консолі, тому контролер просто викликатиме ті ж методи.

## 5 питань про тестування

### 1. Який тест дає найбільшу впевненість у коректності системи?

Інтеграційний тест `RentAndReturn_WithLateFee_ShouldCalculateCorrectly`: він проходить через `RentalService` → `Car` → `Rental.TotalPrice` з реальними доменними об'єктами і перевіряє, що штраф за прострочення нараховано правильно. Це єдиний тест, що валідує повний бізнес-сценарій без моків.

### 2. Як ви мокаєте репозиторії?

Через Moq: `var repo = new Mock<ICarRepository>(); repo.Setup(r => r.GetAll()).Returns(testCars)`. Це дозволяє тестувати `RentalService` і `RentalFacade` незалежно від файлової системи.

### 3. Чому coverage 91%, а не 100%?

Console UI-код (`ConsoleUI`) не покритий E2E input-тестами — введення з `Console.ReadLine()` складно автоматизувати без окремого harness. Натомість вся бізнес-логіка покрита повністю. 100% coverage на UI дало б false confidence без реальної цінності.

### 4. Що таке Theory-тест і навіщо він у вашому проєкті?

`[Theory]` з `[MemberData]` дозволяє запустити один тест для кількох наборів вхідних даних. У розширенні СР29 `CarFilterPipelineTests` перевіряє 4 комбінації фільтрів (порожній pipeline, Available, MaxPrice, AND) одним методом. Без `Theory` довелося б писати 4 окремі методи з дублюванням.

### 5. Що перевіряє `DateProvider` у тестах?

`IDateProvider` — ін'єктований постачальник поточної дати. У тестах підставляється `FakeDateProvider` з фіксованою датою, що дозволяє детерміновано перевіряти логіку прострочення: `rental.DaysOverdue == expectedDays` незалежно від дня запуску.

## 3 питання про компроміси та альтернативи

### 1. Яка помилка була найнебезпечнішою і як ви її контролюєте?

Найнебезпечніша — corrupted JSON file при старті: якщо файл зіпсований, вся система падала. Зараз `JsonDataStore<T>` повертає `Result.Fail` з повідомленням, а `RentalFacade` виводить попередження і продовжує роботу з порожнім репозиторієм. Другорозрядна — некоректний GUID у CLI: тепер `Guid.TryParse` замість `Guid.Parse`.

### 2. Чому `Dictionary` для аналітики, а не лише LINQ GroupBy?

`Dictionary<string, int>` для підрахунку моделей — O(n) прохід з прямим доступом на оновлення. LINQ `GroupBy` також O(n), але виразніший. У поточному проєкті обидва підходи рівнозначні. `Dictionary` обрано там, де результат накопичується інкрементально; `GroupBy` — де потрібна одноразова агрегація над готовою колекцією.

### 3. Що втратили, зробивши `ApplicationEventBus` статичним?

Static state ускладнює тестування: між тестами підписники треба явно знімати, інакше один тест впливає на наступний. Для production-системи правильніше ін'єктувати `IEventBus` через конструктор і реєструвати в DI-контейнері. Для навчального console app static прийнятний, але це свідомий компроміс, зафіксований у FINAL\_REPORT.
